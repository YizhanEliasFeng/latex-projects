\section{iGEM Work Review}

\begin{enumerate}[parsep=0.5\baselineskip] 
  \item I think our project is creative and ambitious, but as an iGEM project its main weakness is overexpansion. It covers too many branches at once, so the core proof of concept is not sharp enough.
  
  \textbf{Main shortages:}
  \begin{enumerate}
    \item The scope is too broad, with too many systems and applications in parallel. There is no single decisive experiment proving the whole concept.
    \item The central engineering cycle is not clear enough.
    \item Dry lab modeling and human practices are interesting, but not tightly linked to design decisions.
    \item Some application claims are too speculative compared with the current evidence.
  \end{enumerate}
  \textbf{Future improvements:}
  \begin{enumerate}
    \item Narrow the project to one core proof of concept, such as light-induced locus seeding with measurable reporter activation.
    \item Organize the work around clearer Design--Build--Test--Learn cycles.
    \item Use modeling to guide concrete construct and assay choices.
    \item Present the system as a reusable platform first, and leave broader applications as future work.
  \end{enumerate}

  \item I am very impressed by McGill 2025's project Cohera. Their project is not just a single application, but a universal platform built around a clear fundamental question: how to construct robust, flexible, and programmable cell-cell adhesion. Its strongest feature is the integration of wet lab, dry lab, and application thinking into one coherent story. The team first defined a general toolbox, then validated its core functions experimentally, and finally used modeling and optimization to improve the system. This makes the project feel both scientifically fundamental and engineering-oriented.

  What we can learn from it is that a strong iGEM project should have a clear core module, a complete engineering logic, and a platform mindset. First, the central question must be simple and memorable. Second, every part of the project should serve the same core goal, instead of expanding in too many directions. Third, dry lab should not exist independently, but should guide design and optimization. Finally, applications should be presented as evidence of the platform's power, rather than replacing the platform itself. In short, the McGill project shows that the most impressive iGEM work is usually not the broadest idea, but the one with the clearest core, the strongest integration, and the best balance between innovation and feasibility.
\end{enumerate}
